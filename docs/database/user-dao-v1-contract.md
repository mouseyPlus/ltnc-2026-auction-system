# UserDAO v1 Integration Contract

This document defines the database/entity contract shared by the Database/DevOps
and OOP team members.

## 1. Database User Mapping

The `USERS` table maps as follows:

| SQLite column | Java type | Database constraint |
|---|---|---|
| `user_id` | `Long` | Integer primary key |
| `username` | `String` | `NOT NULL UNIQUE` |
| `email` | `String` | `NOT NULL UNIQUE` |
| `phone` | `String` | `NOT NULL UNIQUE` |
| `password_hash` | `String` | `NOT NULL` |
| `display_name` | `String` | `NOT NULL` |
| `created_at_utc` | `Instant` | `NOT NULL`, stored as UTC text |
| `is_active` | `boolean` | SQLite integer constrained to `0` or `1` |

`USER_ROLES` maps a user to one or more roles:

| SQLite column | Java type |
|---|---|
| `user_id` | `Long` |
| `role` | `Role` enum stored as text |

`USER_ROLES.role` contains `BIDDER`, `SELLER`, or `ADMIN`. Its composite primary
key is `(user_id, role)`, and its foreign key to `USERS.user_id` uses
`ON DELETE RESTRICT`.

## 2. Role Mapping

The OOP `User` contract must provide a complete `Set<Role>` and preserve every
role during database reconstruction. A user is not limited to one subclass or one
role.

Registration behavior belongs to the service layer:

- Ordinary registration assigns `BIDDER` by default.
- `UserDAO` persists exactly the roles supplied by the `User`.
- `UserDAO` rejects null or empty role sets.
- `ADMIN` assignment is allowed only through authorized service logic.
- Authentication and authorization must not rely on `UserDAO` to infer privileges.

## 3. UserDAO v1 API

`com.auction.database.UserDAO` will use `ConnectionProvider` for connection
access and is expected to expose:

```java
Long createUser(User user) throws SQLException;

Optional<User> findById(Long id) throws SQLException;

Optional<User> findByIdentifier(String identifier) throws SQLException;

boolean updateUser(User user) throws SQLException;

boolean updateRoles(Long userId, Set<Role> roles) throws SQLException;

boolean deactivateUser(Long userId) throws SQLException;
```

The concrete entity and enum types must come from the merged OOP implementation.
All SQLite access methods propagate `SQLException` to the service layer. SQL
exceptions must not be silently converted into `false`, including duplicate
identifier and constraint violations.

## 4. Field Ownership

### Database-managed fields

- `user_id` is generated by SQLite and assigned back to `User` after creation.
- `created_at_utc` is created by the application and must not be changed by
  `updateUser`.
- `is_active` is initially active and changed only through `deactivateUser`.
- Role rows are managed by `createUser` and `updateRoles`.

### Editable through `updateUser`

Only these fields may be changed:

- `username`
- `email`
- `phone`
- `display_name`

`updateUser` must not modify `user_id`, `password_hash`, `created_at_utc`,
`is_active`, or `USER_ROLES`.

### Password management

`UserDAO` does not hash passwords. The service layer hashes the password before
calling `createUser`, and the DAO stores the supplied `passwordHash` unchanged.

### Role authorization

The DAO may persist an `ADMIN` role when authorized internal service code supplies
it. Ordinary registration must not accept or assign `ADMIN`.

### Activation

`deactivateUser` is a soft-deactivation operation that sets `is_active = 0`.
Both active and inactive users must be returned by `findById` and
`findByIdentifier`. Authentication services decide whether to reject inactive
accounts. UserDAO must not physically delete users.

## 5. Transaction Requirements

### User creation

`createUser` must use one transaction:

1. Insert the `USERS` row.
2. Obtain the generated `user_id`.
3. Insert every supplied role into `USER_ROLES`.
4. Commit only after all role inserts succeed.
5. Roll back the user insert if any role insert or constraint operation fails.

The method returns the generated `Long` ID.

### Role updates

`updateRoles` must require a non-null, non-empty role set and use one
transaction:

1. Verify that the user exists.
2. Delete the existing role rows.
3. Insert the complete replacement role set.
4. Commit only after every insert succeeds.

Rollback must restore the original role set. A nonexistent user returns `false`
and creates no role records.

### Transactions and connections

The DAO must preserve the connection's isolation boundary, close connections,
statements, and result sets using try-with-resources, and never commit or roll
back unexpectedly outside the operation's transaction.

## 6. OOP Integration Checklist

The OOP branch must satisfy all of the following before it is merged or used for
`UserDAO`:

- Use Maven source layout under `src/main/java/com/auction/...`.
- Use Java packages rather than classes in the project root `src` directory.
- `User` must contain:
  - `Long id`
  - `String username`
  - `String email`
  - `String phone`
  - `String passwordHash`
  - `String displayName`
  - `Instant createdAtUtc`
  - `boolean isActive`
  - `Set<Role> roles`
- Define `Role` with `BIDDER`, `SELLER`, and `ADMIN`.
- Preserve multiple roles independently of `Bidder`, `Seller`, or `Admin`
  subclasses.
- Provide a complete constructor or factory for reconstructing a persisted user,
  including generated ID, timestamp, active state, password hash, and all roles.
- Provide getters for the database-mapped fields.
- Provide update-oriented setters or immutable replacement methods for the fields
  owned by `updateUser`.
- Provide a supported way to assign the generated database ID after creation.
- Ensure fields and method names are compatible with JDBC mapping.
- Keep entity APIs independent of `ConnectionProvider` and DAO implementation
  details.

## 7. Known Limitations

- The legacy local database migration is not implemented.
- A legacy `USERS` table without `phone` must not be silently migrated or marked
  valid.
- Existing accounts with unknown phones require an explicit migration process;
  no placeholder or invented phone may be used.
- Username, email, and phone are unique within their own columns, but the schema
  does not prevent the same text from appearing across different columns.
  `findByIdentifier` must detect ambiguous cross-column matches rather than
  silently returning an arbitrary row.
- Item, Auction, and Bid entity/DAO integration is a separate task and is not
  part of UserDAO v1.
